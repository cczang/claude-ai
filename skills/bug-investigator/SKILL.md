# Bug Investigator

## Overview

从 bug 描述出发，编排现有分析 skills 完成端到端调查，同时维护调查简报知识库。

**核心原则：经验优先 — 每次分析前先搜索历史简报，相似问题直接快速通道验证，避免重复调查。**

## Sub-Skills

| Skill | 用途 | 何时调用 |
|-------|------|---------|
| `symptom-to-hypothesis` | 症状 → 线索提取 → 排序假设 | 每次调查必用 |
| `eufy-log-analyzer` | 日志提取与搜索 | 有日志文件/zip 包时 |
| `code-tracer` | 追踪函数调用链与诊断日志点 | 需要理解代码流程时 |
| `investigating-device-issues` | 代码+日志联合分析 | 同时有代码和日志时 |
| `systematic-debugging` | 深层根因调查 | 需要系统化调试时 |

## 首次使用 — 配置简报目录

检查 `.opencode/skills/bug-investigator/config.json` 是否存在。

**不存在时，询问用户：**

```
首次使用 bug-investigator。我需要一个目录来保存每次调查的简报。
简报会沉淀症状模式、根因结论和修复经验，后续遇到类似问题时优先参考。

请指定保存路径（例如 /home/zang/src/AnkOutput/investigation-briefs/）：
```

用户回答后：
1. 创建目录（如不存在）
2. 写入配置文件：

```json
{
  "brief_dir": "<用户指定的路径>"
}
```

**已存在时，直接读取 `brief_dir` 进入调查流程。**

## 调查流程

```
Step 0:   搜索历史简报 → 找到相关经验？标记待验证假设
Step 0.5: 确认输入要素 → 缺关键信息则追问
Step 1:   症状分析 → 生成假设（历史根因注入但不跳过）
Step 2:   取证（日志/代码，按可用资源并行）
Step 3:   根因定位
Step 4:   生成简报 → 保存到知识库
```

### Step 0: 搜索历史简报（必须最先执行）

通过索引文件高效检索，而非逐篇 grep 全文。

**索引文件：** `<brief_dir>/index.jsonl`，每行一篇简报的结构化摘要：

```jsonl
{"file": "2026-06-15-p2p-disconnect-after-2h.md", "date": "2026-06-15", "status": "已确认", "device_model": "T9000", "firmware_version": "2.1.7.6", "module": "P2P", "tags": ["P2P", "掉线", "资源泄漏"], "symptom_keywords": ["P2P", "掉线", "断连", "disconnect", "离线", "2小时", "fd"], "root_cause": "P2P 重连时 socket fd 未关闭，2小时后 fd 耗尽", "one_liner": "遇到 P2P 掉线 + 时间累积模式，优先查 fd/内存泄漏"}
```

**检索流程：**

1. **读取 `index.jsonl`**（通常几 KB，全量读入上下文）
2. **从当前 bug 描述提取关键词**（模块名、症状词、错误码、时间模式）
3. **在索引条目中匹配**，按以下置信度降序判断：

| 匹配类型 | 置信度 | 动作 |
|----------|--------|------|
| 同模块 + 同症状关键词命中 ≥2 | 最高 | 读该简报全文，用历史根因作为首要假设 |
| 同模块 + 症状关键词命中 1 | 高 | 读该简报全文，检查是否同底层问题 |
| 不同模块 + 同症状模式 | 中 | 检查是否为系统性问题（如资源泄漏） |
| 仅 `one_liner` 方向相关 | 低 | 作为辅助参考，不跳过全量分析 |

4. **只读取 top 2-3 篇完整简报**（而非全部），节省上下文

**有高置信度匹配时：**
- 向用户展示历史简报摘要（直接从索引的 `root_cause` 和 `one_liner` 呈现，无需打开文件）
- 说明："历史上遇到过类似问题，根因是 [X]。我会优先验证这个方向，同时考虑其他可能。"
- 读取该简报全文，记录历史根因作为 **待验证首选假设**，传递给 Step 1

**⚠️ 禁止跳过 Step 1。** 历史经验提供方向，不替代假设生成。原因：
- 同一症状在不同设备/版本上根因可能完全不同
- 跳过假设生成会导致锚定偏差 — 只看到历史根因，忽略新可能性

**无匹配时：** 正常进入 Step 0.5 → Step 1。

**索引不存在时：** 跳过 Step 0（首次调查），Step 4 会创建索引文件。

### Step 0.5: 确认输入要素

在开始分析前，检查 bug 描述中是否包含以下关键信息。**缺少的项主动追问用户**：

| 要素 | 说明 | 必需 |
|------|------|------|
| **设备型号** | T7000/T8000/T9000 等，不同平台硬件差异大 | 是 |
| **固件版本** | 同一现象在不同版本根因可能不同 | 是 |
| **复现率** | 必现/偶发/仅一次 — 决定走日志分析还是加桩复现 | 是 |
| **最近变更** | OTA 升级、配置修改、环境变化 — 指向回归问题 | 建议 |
| **日志/core dump** | 有无现场证据 — 决定取证路径 | 建议 |

**追问模板（缺少必需项时使用）：**
```
开始分析前需要确认几个关键信息：
1. 设备型号是什么？（如 T9000/T8030）
2. 当前固件版本？
3. 问题是必现还是偶发？大概多少概率？
[根据缺失项选择性追问]
```

**所有必需项确认后，进入 Step 1。** 建议项缺失不阻塞流程，但在简报中标注"未提供"。

### Step 1: 症状分析 → 假设生成（不可跳过）

使用 `skill` 工具加载 `symptom-to-hypothesis`，按该 skill 的指令执行其三步流程：

1. **提取线索** — 从 bug 描述中提取时间模式、触发条件、恢复方式等线索
2. **生成排序假设** — 按线索匹配度排序 3-5 个假设
3. **设计验证步骤** — 按成本从低到高排列

**如果 Step 0 找到了历史匹配：**
- 将历史根因作为 **首选假设**（排在第一位，标注"来源：历史简报 YYYY-MM-DD"）
- **但仍必须生成至少 2 个替代假设** — 防止历史经验掩盖新问题

### Step 2: 取证（按可用资源选择路径）

根据用户提供的资源，用 `skill` 工具加载对应 skill，按该 skill 指令执行。**同一时刻只加载一个 sub-skill**，避免多 skill 指令冲突。

```
有日志 + 有代码 → skill("investigating-device-issues")
只有日志       → skill("eufy-log-analyzer")
只有代码       → skill("code-tracer")
都没有         → 基于假设给出验证步骤，请用户补充资料
```

**取证目标：** 验证或排除 Step 1 生成的假设，收集根因证据。

**取证时对照假设清单逐项检查：**
- 该假设的验证步骤是什么？
- 日志/代码中看到了什么？
- 是否能确认或排除该假设？

### Step 3: 根因定位

如果 Step 2 已确认根因 → 直接进入 Step 4。

如果仍不确定，用 `skill` 工具加载 `systematic-debugging`，按其四阶段流程执行：
- Phase 1: 根因调查（数据流追踪）
- Phase 2: 模式分析（对比工作/故障代码）
- Phase 3: 假设验证（最小化测试）

### Step 4: 生成调查简报（必须执行）

调查完成后，**必须**生成简报保存到知识库。

**文件命名：** `<YYYY-MM-DD>-<简短描述slug>.md`
**保存路径：** `<brief_dir>/<文件名>`

**简报模板：**

```markdown
# [问题简述]

**日期：** YYYY-MM-DD
**状态：** 已确认 / 待复现 / 需补充信息
**设备型号：** [如 T9000/T8030]
**固件版本：** [如 2.1.7.6]
**标签：** [模块名], [症状类型], [根因类别]

## 症状

[原始问题描述，保留所有线索细节]
- 时间模式：[如有]
- 触发条件：[如有]
- 恢复方式：[如有]
- 影响范围：[如有]
- 复现率：[必现/偶发/仅一次]

## 假设与验证

| # | 假设 | 验证方法 | 结果 |
|---|------|---------|------|
| 1 | [假设描述] | [验证操作] | ✅ 确认 / ❌ 排除 |
| 2 | ... | ... | ... |

## 根因

[一句话根因]

**详细分析：**
[机制解释 — 为什么会发生，代码层面的逻辑]

## 关键证据

**日志证据（如有）：**
```
[完整日志行，不裁剪]
```

**代码证据（如有）：**
- 文件：[路径]
- 函数：[函数名]
- 关键逻辑：[说明]

## 修复方案

[已实施的修复 或 建议的修复方向]

## 经验总结

[一句话：下次遇到 [症状] 时，优先检查 [方向]]
```

**简报写完后，追加索引条目到 `<brief_dir>/index.jsonl`：**

```jsonl
{"file": "<文件名>.md", "date": "YYYY-MM-DD", "status": "已确认", "device_model": "T9000", "firmware_version": "2.1.7.6", "module": "<主模块标签>", "tags": ["<模块>", "<症状类型>", "<根因类别>"], "symptom_keywords": ["<关键词1>", "<同义词>", "<错误码>", "..."], "root_cause": "<一句话根因>", "one_liner": "<经验总结：遇到[症状]时优先检查[方向]>"}
```

**`status` 取值：**
- `已确认` — 根因已定位，有修复方案
- `待复现` — 排查到一定程度但需要更多现场数据
- `需补充信息` — 缺少日志/core dump/复现步骤，无法继续

**`symptom_keywords` 编写要求 — 这是检索的关键：**
- 必须包含简报中出现的模块名、症状描述词
- **必须补充同义词/近义词**：如 "掉线" → 同时加 "断连"、"离线"、"disconnect"
- 包含相关错误码、函数名等精确标识符
- 包含时间/频率模式词：如 "2小时"、"偶发"、"重启恢复"

**索引文件不存在时自动创建。**

**索引条目质量自检（写入前必须执行）：**
1. `symptom_keywords` 数量 ≥ 5？不足则补充
2. 是否包含至少 1 个英文同义词（如 disconnect/crash/timeout）？缺少则补充
3. `device_model` 和 `firmware_version` 是否已填写？未提供则标注 "unknown"
4. `status` 是否准确反映调查结论？

**最后告知用户：**
```
调查简报已保存到：<完整路径>
索引已更新（共 N 篇简报）
```

## 标签分类参考

用于简报的标签字段，便于后续检索：

**模块标签：**
`DEVMGR`, `P2P`, `STRATEGY`, `ES2`, `OTA`, `PUSH`, `AI_AGENT`, `NV`, `NET`, `DISPLAY`, `MEDIA_PUSH`

**症状类型：**
`掉线`, `崩溃`, `黑屏`, `卡顿`, `超时`, `内存泄漏`, `无响应`, `数据丢失`, `推送失败`, `OTA失败`, `添加失败`, `报警异常`

**根因类别：**
`资源泄漏`, `竞态条件`, `状态机异常`, `配置错误`, `协议不匹配`, `超时参数不合理`, `空指针`, `缓冲区溢出`, `线程死锁`, `外部依赖故障`

## Common Mistakes

| 错误 | 正确做法 |
|------|----------|
| 跳过历史简报直接分析 | Step 0 是**必须**步骤，相似案例可节省 80% 时间 |
| 历史匹配后跳过 Step 1 假设生成 | **禁止跳过**。历史根因注入为首选假设，但必须生成 ≥2 个替代假设 |
| 不追问设备型号和固件版本就开始分析 | Step 0.5 确认关键要素，不同平台/版本根因可能完全不同 |
| 调查完不写简报 | Step 4 是**必须**步骤，不写 = 经验无法积累 |
| 简报只写结论不写症状 | 症状部分是未来检索的关键，必须详细 |
| 简报不记录设备型号和固件版本 | 缺少环境上下文的简报会导致跨平台误匹配 |
| 简报标签写得太笼统 | 用上面的分类参考，保持一致性 |
| 索引 symptom_keywords 少于 5 个 | 自检不通过则补充，必须包含同义词和英文关键词 |
| 问题未定论时不写简报 | 未确认根因也要写简报，status 标为「待复现」或「需补充信息」 |
| 同时加载多个 sub-skill | 一次只加载一个 sub-skill 执行，避免指令冲突 |
| 只用一个 skill 完成调查 | 按可用资源依次加载对应 skill，覆盖代码+日志+假设 |
