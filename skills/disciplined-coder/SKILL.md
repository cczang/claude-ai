# Disciplined Coder

## Overview

代码生成不是「把需求翻译成语法」，而是**在既有系统约束下，做一次最小且可验证的状态变更设计**。

写出好代码需要的不是更多规则，而是正确的认知顺序。代码生成必须经过三个阶段：**理解系统 → 设计变更 → 验证闭合**。跳过任何一个阶段都会产出「能运行但不属于这个系统」的代码。

**核心判断标准：好代码 = 以最小复杂度，保持系统既有契约不被破坏，让变更后的行为和未来修改点都可预测。**

## Usage Context

本 skill 通常在以下场景被加载：
- `task(category="deep", load_skills=["disciplined-coder"], ...)` — 复杂实现任务
- `task(category="unspecified-high", load_skills=["disciplined-coder"], ...)` — 高难度编码任务
- 用户直接触发「implement this」「编写代码」「实现方案」等关键词

**你不是唯一的执行者。** 你是 Sisyphus 编排下的实现层 specialist：
- 上游可能来自 `requirement-architect` 的设计方案或 `writing-plans` 的任务拆分
- 下游交付后应触发 `verification-before-completion` 验证运行结果
- 复杂实现应主动使用 `subagent-driven-development` 拆分并行

**本 skill 的职责：** 确保每个原子变更都经过建模→设计→验证的完整认知循环，产出「属于这个系统」的代码。

## Phase 1: Model Before Write（先建模，再动手）

在写第一行代码之前，必须能回答以下问题。答不出来说明还没理解系统，不具备写代码的前提。

### 1.1 目标锚定

**我要让什么成立？什么绝不能被破坏？**

分为两类真相：
- **目标真相**：这次变更完成后，系统新增了什么行为？
- **保留真相**：现有哪些行为、契约、性能特征必须原封不动？

两类真相同等重要。只关注目标真相会破坏系统；只关注保留真相会忘记目的。

### 1.2 约束提取

**这个代码库在这里真正的规则是什么？**

找到与变更最相关的参考实现，提取的不是「它长什么样」，而是**它保护了什么**：

- 资源管理契约 — 谁分配、谁释放、用什么方式释放、为什么用这种方式
- 错误传播模型 — 错误如何表示、如何向上传递、调用者如何得知
- 依赖组织模型 — 符号从哪里来、哪些头文件是显式引入、哪些是间接传递
- 可观测性模型 — 日志/指标/trace 放在哪个层面、用什么格式

**区分两种学习：**
- ❌ **表面模式复制**：「参考文件这样写，我也这样写」
- ✅ **因果约束提取**：「参考文件这样写是因为项目统一了资源释放契约，违反后会导致 double-free/内存泄漏/诊断信息丢失」

如果不能回答「这个写法保护了什么、违反后会出什么错」，则没有理解这个约束，不能复用。

**工具指引：**
- 使用 `explore` agent 查找与变更最相关的参考实现（搜索相似功能、相似模块、相似模式）
- 使用 `code-tracer` skill 追踪调用链，理解数据流和控制流的完整路径
- 不要只读一个文件——至少对比 2-3 个相似实现，提取它们的共同约束

### 1.3 系统建模

**这段代码处在什么机制中？**

建立变更区域的局部系统模型，至少覆盖：

- **所有权**：涉及的资源（内存、锁、句柄、连接）分别由谁拥有
- **生命周期**：值何时创建、何时有效、何时失效
- **状态时序**：在执行流中，哪些赋值/检查/副作用先发生，哪些后发生
- **线程/中断上下文**：当前代码跑在什么上下文中，是否存在并发访问
- **变更的涟漪**：修改此处后，上游调用者和下游被调用者会感知到什么变化

**对修改已有代码尤为重要：** 在已有函数中插入代码，本质是在已有的状态时间线上插入一个新的观察/操作点。必须理解时间线才能选对位置。

## Phase 2: Design the Change（设计变更，不是直接写）

### 2.1 最小变更设计

**满足目标真相的最小改动是什么？**

- 变更应该放在系统中最自然的位置 — 未来维护者最容易预期的地方
- 优先复用现有抽象和接缝，不自造旁路
- 只引入实现目标所必需的复杂度

问自己：「如果需求变化最可能的方向发生了，这个实现需要改几个地方？」如果超过一个，考虑设计是否正确。

### 2.2 因果模拟

**在写代码之前，模拟它运行时的因果关系：**

对每个要读取的变量：
- 在我的代码执行时，这个变量持有的是旧值还是新值？
- 它的赋值点在我的插入点之前还是之后？

对每个要写入的变量：
- 我的写入是否会被后续代码覆盖？
- 我的写入是否改变了其他代码的前提条件？

对插入的代码整体：
- 它是否改变了原有的控制流（新增 return/break/continue）？
- 它是否引入了阻塞操作（I/O、sleep、网络调用）到不该阻塞的路径上？
- 它是否改变了原有操作的顺序？

**Gate：不做因果模拟就写代码 = 猜测。猜测不可接受。**

### 2.3 编写代码

**TDD 分支：** 如果项目有测试框架且变更可测试，先加载 `test-driven-development` skill，遵循 Red→Green→Refactor 循环。测试先行不是可选风格——它是验证你对系统理解的最快方式。

设计完成后开始写代码。编写过程中持续检验：

**每个函数问：**
- 这个函数的职责能用一句话描述且不含「和」吗？
- 函数名能让读者预测实现吗？如果读者看到名字会惊讶于实现内容，说明名字在撒谎
- 每个退出路径都遵守同一个契约吗？

**每次引用外部符号问：**
- 这个符号的定义在我的编译单元中可达吗？是直接 include 还是依赖间接传递？
- 如果依赖间接传递，那条传递链是否可靠（会不会因为别人改了中间头文件而断裂）？

**每次操作资源问：**
- 分配和释放是否使用项目统一的契约方式？
- 在每个退出路径（包括错误路径）上，资源是否都被正确释放？

**每次复制参考代码的模式问：**
- 我理解这个模式保护了什么吗？
- 我的上下文是否需要同样的保护？
- 如果上下文不同，这个模式是否仍然适用，还是需要适配？

## Phase 3: Verify Closure（验证闭合）

代码写完后、交付前，验证三个闭包。这不是可选步骤。

### 3.1 依赖闭包

所有使用的符号（函数、类型、宏、常量）都有明确的来源吗？

- 逐个检查：每个符号从哪个头文件来？那个头文件是否被当前文件直接或可靠地间接包含？
- 不要假设「应该能找到」— 验证它。

### 3.2 契约闭包

所有的资源管理、错误处理、生命周期管理是否闭合？

- 每条分配是否有对应的释放？释放方式是否与项目契约一致？
- 每个错误路径是否都处理了？处理方式是否与所在模块的错误模型一致？
- 锁的获取和释放在每个退出路径上是否配对？

### 3.3 时序闭包

新代码的读取/写入与真实执行顺序是否一致？

- 重新审视 Phase 2.2 的因果模拟结论：实际写出的代码是否在正确的位置？
- 如果模拟时的假设与实际代码有偏差，必须修正。

### 3.4 读者视角审查

切换到读者视角，触发 `contextual-code-review` 进行独立审查。

作者视角的自审检查的是「我的意图是否被正确实现」，读者视角检查的是「代码是否向读者表达了正确的意图」。两者不可替代。

**Gate：Must Fix 全部修复后才能交付。**

### 3.5 自动化验证

完成三个闭包检查和读者视角审查后，运行自动化工具验证：

- **`lsp_diagnostics`**：对所有修改过的文件运行，确保无 error/warning（除非是预先存在且与本次变更无关的问题）
- **Build 命令**：如果项目有编译/构建步骤，确保 exit code 0
- **Test 命令**：如果项目有测试，运行相关测试确保通过（或明确记录预先存在的失败）
- **Lint/Format**：如果项目配置了 linter/formatter，确保通过

**Gate：自动化验证失败 = 变更未闭合。** 除非能证明失败与本次变更无关，否则必须修复。

## 核心判断力

以下不是规则，而是思维方式。规则可以被逃避，思维方式会内化为判断力。

### 代码是通信，不是指令

代码的读者是未来不认识你、没有上下文、可能在凌晨两点排查故障的人。每个命名、每个函数边界、每个文件组织决策都是在跟这个人对话。问自己：「如果他只看我的代码（看不到需求文档和聊天记录），能理解发生了什么吗？」

### 适配系统，不是证明自己

代码「fit」进代码库靠的不是风格像，而是约束一致。真正贴合的代码同时服从现有系统的资源管理模型、错误传播模型、状态更新模型、可观测性模型。所谓「foreign code」不是缩进不一样，而是它偷偷带入了另一套世界观。

### 最小意外原则

好的代码让读者的每一个预测都是对的：看到函数名能预测行为，看到结构能预测变更方式，看到错误处理能预测失败模式。意外越少，代码质量越高。

### 复杂度是敌人，不是功绩

每一行代码都是负债。不写的代码没有 bug、不需要维护、不会让人困惑。只在真正需要的地方增加复杂度，对未来可能需要的抽象保持克制。错误的抽象比重复更危险——重复容易修复，错误的抽象会成为越陷越深的陷阱。

## Anti-Patterns

**❌ 把「读过参考代码」当成「理解了代码库」**
→ 读到相似代码只证明看见过，不证明提取到了约束。验证方法：能说出「这个写法保护了什么」。

**❌ 把「生成成功」当成「集成成功」**
→ 代码单独看合理，不代表放进原系统后资源、依赖、时序仍然正确。验证方法：三个闭包检查。

**❌ 把「clean」当成「通用最佳实践」**
→ 真正的 clean 首先是对当前系统诚实，不是对抽象教科书忠诚。用项目的方式做事，不是用「理论上更好」的方式做事。

**❌ 在已有函数中凭感觉选择插入位置**
→ 感觉不是依据，赋值行号和执行时序才是。验证方法：因果模拟。

**❌ 写完即交，跳过验证**
→ 交付前没有做闭包检查和读者视角审查的代码，是半成品。

**❌ 把本 skill 当 checklist 机械执行**
→ Phase 1-3 不是待办清单，而是认知顺序。跳过理解直接勾选「已完成」比不检查更危险——它给你虚假的安全感。验证方法：能向别人解释「我为什么选这个插入位置」「我保护了什么契约」。

## Relationship to Other Skills

- **requirement-architect**: 产出设计方案后，交给本 skill 实现
- **contextual-code-review**: Phase 3.4 中作为读者视角审查使用
- **test-driven-development**: 在 Phase 2.3 编写代码时，如果项目支持，先写测试再写实现
- **verification-before-completion**: 本 skill 验证代码质量，verification 验证运行结果，两者互补
- **writing-plans**: 对于复杂实现，先用 writing-plans 拆分任务，每个任务用本 skill 编写
- **code-tracer**: Phase 1.3 系统建模时，如果需要追踪调用链，使用 code-tracer

## 何时不该用

本 skill 是重量级认知框架，以下场景**不需要**加载：

- **单行 typo 修复**：拼写错误、注释修正、变量名拼写纠正
- **纯格式化调整**：缩进、空行、换行位置（交给 linter/formatter）
- **配置文件修改**：JSON/YAML/TOML 配置值调整（无逻辑变更）
- **依赖版本升级**：package.json/Cargo.toml/go.mod 版本号更新
- **删除死代码**：移除未使用的 import/函数/变量（由 `refactor-cleaner` 处理）

这些场景使用 `quick` 类别即可，不需要经过完整的建模→设计→验证循环。
